# 계획 문서 기준

큰 작업은 코드를 쓰기 전에 계획 문서를 먼저 작성한다. 결정과 이유가 남아야 나중에 세션이 바뀌어도 이어서 작업할 수 있다.

## 계획 문서가 필요한 경우

- DB 스키마 변경 (Supabase 마이그레이션, RLS 정책)
- 프론트·DB·Edge Function 등 여러 계층에 걸친 기능
- 되돌리기 어렵거나 사용자 데이터에 영향이 있는 변경 (데이터 형식 변경, 인증 방식 변경)
- 접근 방법이 두 가지 이상이라 선택이 필요한 작업

## 필요 없는 경우

- 한 계층 안에서 끝나는 변경 (화면 하나 수정, 추출 로직 버그 수정)
- 테스트 추가, 리팩터링, 문서 수정

## 위치와 이름

- 진행 중: `docs/exec-plans/active/YYYY-MM-DD-<slug>.md`
- 완료 후 `docs/exec-plans/completed/`로 이동하고 맨 위에 결과 한 줄을 적는다
- 작업 중에 내린 아키텍처 결정은 `docs/adr/`에 따로 기록한다

## 템플릿

```markdown
# <작업 이름>

- 상태: 진행 중 | 완료 | 중단
- 시작: YYYY-MM-DD

## 배경
왜 이 작업이 필요한가.

## 목표
- 끝났을 때 사용자가 할 수 있는 것

## 비목표
- 이번에 하지 않는 것 (범위가 커지는 것을 막기 위해 명시)

## 현재 상태
관련 코드·데이터가 지금 어떻게 되어 있는가.

## 계획
1. 단계별 작업. 각 단계는 독립적으로 커밋 가능한 크기로

## 데이터·마이그레이션
스키마 변경, RLS, 기존 데이터 처리. 없으면 "없음".

## 테스트
- 먼저 작성할 실패 테스트
- 검증 명령과 기대 결과

## 롤백
문제가 생기면 어떻게 되돌리는가.

## 진행 기록
- YYYY-MM-DD: 한 일, 바뀐 결정
```
